## 0. 先建立 3 个关键认知（为什么大模型测试不一样）

| 传统软件测试                 | 大模型测试                                       |
| ---------------------- | ------------------------------------------- |
| 输入确定 → 输出确定（同一输入永远同结果） | **非确定性**：同输入多次跑，措辞/步骤/成败可能不同                |
| 有「唯一正确答案」可断言           | 多数场景**没有唯一正确答案**，需「裁判模型(LLM-as-Judge)」或人工评分 |
| 黑盒测功能、白盒测代码            | 常需**被评模型 + 裁判模型分离**（裁判用更强模型打分）              |
| 功能 / 性能 / 安全为主         | 多了**能力、鲁棒性、公平性、幻觉、合规、越权、Agent 轨迹**等维度       |
| 用例即脚本                  | **Benchmark 数据集本身就是测试用例**（MMLU 等）           |

**上手路径（建议顺序）**

1. 明确被测对象类型：纯模型 / RAG 应用 / Agent / 通用 AI 应用。
2. 跑通最小可执行套件：能力评测（test_01）+ 安全/幻觉（test_03），用本地 mock 或公有 OpenAI 兼容端点。
3. 对照第 1 章「11 模块清单」逐条勾选本次需覆盖的测试点，缺哪补哪。
4. 把用例接进 CI，做到「模型/模板/数据一变更就回归」。

## 1. 大模型测试全景：11 个测试维度（测试点清单）

> 任何评测任务，先按本清单逐模块勾选，防止遗漏维度。每模块给出：**测什么 / 怎么测 / 判定标准 / 真实来源**。

### 模块 1：评测数据集与离线能力评测

- **测什么**：任务覆盖、难度梯度、领域多样、语言风格四类完整性（缺维度→结论不可信）；模型知识广度与推理。
- **怎么测**：用 OpenCompass / lm-evaluation-harness 跑标准 Benchmark；按 4 项完整性清单逐条核对数据集。
- **判定**：数据集缺维度则结论不可信；能力分需达业务准入门禁（如 acc_norm ≥ 0.5~0.6，按模型档位定）。
- **来源**：MMLU、C-Eval、CMMLU、FlagEval、SuperCLUE、OpenCompass、HELM。

### 模块 2：数据质量与公平性

- **测什么**：一致性（逻辑/标注/格式）、有效性（事实/相关/无偏）、公平性（刻板/歧视）。
- **怎么测**：自动校验 + 人工 Review；敏感属性替换、偏见词分析、平等指标（统计平等/机会平等/结果平等）。
- **判定**：标注一致率达标；刻板分/DPD/EOD 达标。
- **来源**：StereoSet、BOLD、BBQ、WinoBias、DiscrimEval、GenderCARE、TrustLLM(fairness)。

### 模块 3：鲁棒性 · 泛化 · 时效性

- **测什么**：拼写错误/口语/噪声/对抗扰动下的稳定性；域外与零少样本泛化；知识截止后事件。
- **怎么测**：PromptBench 四级攻击（字符→语义）；GLUE-X 域外；FreshQA 时效性问题。
- **判定**：词级攻击掉点 < 33%；未训练分布可泛化；未知事件应「不知道」而非幻觉。
- **来源**：PromptBench(arXiv:2306.04528)、FreshQA、GLUE-X。

#### PromptBench 四级扰动详解（NeurIPS 2023，4788 个对抗提示，13 个数据集）

| 扰动级别               | 手法                  | 模拟场景         | 实测影响                     | 用例示例                                           |
| ------------------ | ------------------- | ------------ | ------------------------ | ---------------------------------------------- |
| **字符级（Character）** | typo、字符替换/调换、随机字符   | 用户手滑打错       | 浅层噪声，大多靠意图识别兜底能救回        | "关掉蓝牙"→"关掉蓝呀"/"关掉蓝牙  "                         |
| **词级（Word）**       | 同义词替换、插入噪声词、词汇变形    | 合法但非标准表述     | **掉点最猛（~33%）**，模型对关键词最敏感 | "把QQ音乐卸载了"→"那个听歌软件你帮卸了呗"                       |
| **句子级（Sentence）**  | 改写句式、插入无关干扰句、调整短语顺序 | 主题不变但加了"废话"  | 冗余信息下指令抽取                | "查一下腾讯今天的股价"→"我随便看看，你顺手帮我查下腾讯今天股票收多少，反正闲着也是闲着" |
| **语义级（Semantic）**  | 深度重写但保留任务意图         | 同一件事用完全不同的说法 | 对长任务（含多步操作）影响最大          | "帮我把桌面上的发票按月份归整"→"桌面上那些报销单据，按月份给我分分类放好"        |

> **实测规律**：词级扰动最容易导致 **Skill 误选**（关键词被替换后 PM 路由到错误子 Agent）；字符级大多靠纠错兜底；语义级对长任务影响最大。鲁棒性评测用例按四级构造，**词级和语义级是重点**。

> **重要边界**：鲁棒性（输入噪声，用户无心之失）**在你的测试范围**；安全红队（Prompt 注入/Jailbreak，有意误导）**有专门团队负责，不在范围**。别把鲁棒性说成安全。


### 模块 4：Agent 专项能力

#### 4.0 基础测试点

- **测什么**：任务规划、死循环、短期记忆、记忆污染/遗忘、自助风险决策、不可逆操作保护、角色/功能越权。
- **怎么测**：AgentBench/GAIA 多步任务；制造工具持续失败看是否优雅退出；跨轮追问；唯一标识并发；不可逆操作需显式确认。
- **判定**：达 max_steps 不崩且有终态；越权/不可逆操作被拒绝或先确认。
- **来源**：AgentBench(arXiv:2308.03688)、GAIA(arXiv:2311.12983)、τ-bench(arXiv:2406.12045)、BFCL。

#### 4.1 多 Agent 架构模式（面试必知）

单 Agent → 多 Agent 的核心是"把复杂任务拆给不同角色/不同推理策略去解"。

**单 Agent 推理范式**：

| 范式                                                          | 核心思想                            | 优点                | 缺点            | 适用场景           |
| ----------------------------------------------------------- | ------------------------------- | ----------------- | ------------- | -------------- |
| **ReAct**（Yao et al., ICLR 2023, arXiv:2210.03629）          | Thought→Action→Observation 交替循环 | 实时调整、低延迟          | 复杂多步任务易"丢失目标" | 绝大多数 Agent 的基石 |
| **Plan-and-Execute**                                        | 先生成完整步骤计划，再逐步执行                 | 逻辑严密、减少漂移、Token 省 | 延迟高、计划僵化      | 复杂自动化流程        |
| **Reflexion**（Shinn et al., NeurIPS 2023, arXiv:2303.11366） | ReAct 后加自我批判，发现问题改了再跑           | "第一版很少最优"的场景下效果好  | 多一轮 Token 消耗  | 代码生成、多步研究      |
| **Tree of Thoughts**                                        | 并行探索多条推理路径，遇死胡同回溯               | 适合探索空间大的问题        | Token 消耗最大    | 数学证明、复杂调试      |

**多 Agent 拓扑**：

| 拓扑                           | 结构                          | 典型框架                         | 测试关注点               |
| ---------------------------- | --------------------------- | ---------------------------- | ------------------- |
| **Supervisor（编排者+工作者）**      | manager 拆解任务→派给专门 worker→汇总 | CrewAI hierarchical, AutoGen | 任务拆解正确性、上下文 handoff |
| **Router（路由分发）**             | 按意图路由到合适 Agent              | —                            | 路由准确性、误选率           |
| **Blackboard（共享黑板）**         | Agent 通过共享存储传递上下文           | —                            | 数据一致性、可审计性          |
| **Peer collaboration（对等协作）** | Agent 平等协商                  | —                            | 共识机制、死锁             |

> **反直觉结论**：Multi-Agent 不一定比 Single-Agent 好。线性确定性任务用硬编码 Prompt Chain 比复杂路由更可靠更便宜。判断标准三条——任务是否有不确定性分支、是否需要对抗性审查、是否需要多专业领域知识。三条都不占，别上多 Agent。

#### 4.2 Agent 记忆测试

| 记忆类型     | 位置             | 测什么                     | 测试方法                                  |
| -------- | -------------- | ----------------------- | ------------------------------------- |
| **短期记忆** | 当前上下文窗口        | 跨轮指代消解（"换成刚才那个文件"）、多轮一致 | 埋约束→插无关轮→触发约束                         |
| **长期记忆** | 外部持久化（向量库+RAG） | 召回相关性、过时/错误知识、知识时效性     | FreshQA 时效性 + RAGAS context_precision |
| **工作记忆** | 当前任务的中间状态      | 状态在长链路里是否"被挤出窗口而遗忘"     | 跨模块长任务链路测试                            |

**记忆污染/遗忘测试**（高频坑）：

| 测试点             | 方法                               | 预期               |
| --------------- | -------------------------------- | ---------------- |
| 唯一标识并发          | 多个会话用同一用户 ID，看记忆是否串              | session_id 隔离，不串 |
| 超长对话截断          | 上下文撑到接近窗口上限，验证关键约束在末尾轮是否仍被遵守     | 关键约束不被挤出         |
| τ-bench DB 状态对比 | 多轮工具调用后对比"系统真实状态"和"Agent 自以为的状态" | 一致，无记忆漂移         |

#### 4.3 工具调用 / Function Calling 测试

| 测试维度         | 测什么                              | 判定              | 参照                       |
| ------------ | -------------------------------- | --------------- | ------------------------ |
| 工具选择正确       | 该调 A 却调了 B / 调了无关工具              | 工具名与意图匹配        | BFCL"无关函数识别"             |
| 参数 schema 校验 | 参数符合 JSON schema，必要字段不缺、类型对、枚举合法 | schema 完全符合     | 自定义 ActionAccuracyMetric |
| 调用顺序         | 关键顺序符合预期（如搜索→预订），允许中间穿插          | 子序列断言通过         | 轨迹断言                     |
| 错误恢复         | 工具返回失败/超时/半截 JSON 时，Agent 不崩溃    | 优雅重试/换路/降级，不死循环 | —                        |
| 终态/无死循环      | 到达终态且有 final answer              | 未触顶 max_steps   | —                        |

#### 4.4 规划与反思能力测试

- **计划可解释**：让 Agent 输出 step 列表，检查是否覆盖目标、有无明显遗漏
- **执行正确**：照 4.3 工具调用测试走
- **纠偏**：执行中某步失败，Agent 是否调整后续计划而不是硬走原 plan

**死循环防护（必测项）**：

- 制造"工具持续失败"场景，看 Agent 是否在 max_steps 内优雅退出、给出"做不到"的诚实回答
- 用 τ-bench pass^k 思路：同一任务跑 k 次，看是否每次都能在步数上限内稳定到达终态
- 区分"还在思考"和"死循环"：连续 N 步工具调用和参数高度相似且无 Observation 进展 → 卡死
- Reflexion 测试：给一个第一次失败的任务，看 Agent 第二次是否基于 critique 改了策略（不是盲目重试）

#### 4.5 多 Agent 协作诊断方法（二分法）

多 Agent 系统出问题时，用**二分法：先隔离→再溯源→后归因**，把"Agent 自身逻辑问题"和"协作链路问题"当成两个互斥假设，用受控实验逐个排除。

| 方法               | 作用       | 操作                                                                   |
| ---------------- | -------- | -------------------------------------------------------------------- |
| **轨迹断言**         | 定位基石     | 录完整轨迹（PM 拆解→路由→每 Agent 工具调用/参数/返回→终态），冲突点在哪一跳一眼可见                    |
| **单 Agent 隔离复跑** | 区分个体还是协作 | 出问题的子任务单独丢给对应 Agent 跑（绕过 PM）：单独跑就失败→Agent 自身问题；单独成功组队失败→协作链路问题       |
| **路由决策回放**       | 定位 PM    | 固定 temperature=0 + seed，同一意图反复跑 PM 拆解：结果不稳定→PM 意图理解 bug；稳定但错了→分类规则问题 |
| **随机性控制**        | 排除偶发     | 控温到 0 看是否必现：必现→确定性 bug；仍偶发→模型概率行为，靠共识/重试/投票兜底                        |
| **GEval 分段打分**   | 精确定位断裂点  | 对轨迹每段用 GEval 配 rubric 打分，得分最低段就是根因层                                  |

> **前提条件**：二分法依赖可观测性（trace_id 串联各 Agent 工具调用），没埋点这套方法跑不起来。

#### 4.6 评测指标全景（五层指标 + Gate 阈值）

| 指标层        | 指标                           | 测什么                        | 推荐阈值/说明                  |
| ---------- | ---------------------------- | -------------------------- | ------------------------ |
| **任务层**    | 任务成功率、子任务完成率                 | 端到端是否达成目标                  | 核心操作近乎 100%              |
| **工具层**    | 工具调用准确率、必要工具覆盖率、参数正确率        | Q4.3 工具调用测试产出              | 参数正确率 ≥ 0.9              |
| **效率层**    | 平均步数、Token 消耗、TTFT/TPOT      | 越少越高效                      | TTFT < 1s（常规）            |
| **稳定性层**   | stochastic run×N 通过率（pass^k） | 同一用例跑 N 次的稳定性              | ≥ 0.8（高风险提至 0.95+）       |
| **质量/安全层** | 幻觉率、异常输入不崩溃率                 | Faithfulness/Hallucination | Faithfulness ≥ 0.8（面向用户） |

**Gate 阈值制定原则**（重点）：

1. **不能照搬库默认值**：DeepEval faithfulness 默认 0.5 偏低，面向用户内容建议 ≥ 0.8
2. **按模型档位与业务设**：核心功能必须 100% 程序化校验通过；开放生成类放宽到合理区间
3. **阈值可解释、可回溯**：每个阈值写清为什么，别拍脑袋
4. **可程序校验的操作近乎 100% 门禁**；开放生成类用 faithfulness/answer_relevancy 区间门禁

### 模块 5：功能测试 Checklist

- **测什么**：Prompt 理解、参数边界(temp/top_p/max_tokens)、上下文处理、角色错乱、异常输入、输出质量。
- **怎么测**：等价类 + 边界值 + 异常注入；多轮一致性、指代消解、关键约束不丢失。
- **判定**：异常输入不崩溃、合理提示；角色不漂移；输出准确/相关/完整/格式合规。

### 模块 6：性能测试（分层指标）

- **测什么**：用户感知层(TTFT/TPOT)、系统层(Token·s/QPS/并发)、资源层(GPU/CPU/内存)、长上下文、稳定性、会话隔离。
- **怎么测**：evalscope / LMDeploy / vLLM + Locust 压测；4K→128K 梯度与 OOM 观察；80% 峰值跑数小时。
- **判定**：TTFT 常规 < 1s；P95/P99 达标；长上下文无 OOM；并发会话不串扰。
- **来源**：evalscope、LMDeploy、ChatBench、τ-bench(会话隔离)。

### 模块 7：安全测试（应用 / 数据 / 模型三层）

- **测什么**：应用层(Prompt 注入/Jailbreak/提权)、数据层(泄露/向量库攻击/API Key 泄露)、模型层(窃取/对抗/后门/投毒)；垂直/水平/功能越权。
- **怎么测**：TrustLLM、JailbreakBench、Promptfoo 红队、garak 100+ 攻击探针；间接注入（上传含隐藏指令的图片/文档）。
- **判定**：注入/越权应被识别拒绝；敏感信息不泄露。

### 模块 8：Prompt 工程与回归

- **测什么**：Prompt 有效性/一致性/鲁棒性/安全性；模型升级前后退化/漂移/幻觉/安全降低；A/B。
- **怎么测**：用例库覆盖 + 多次运行比一致性(Promptfoo)；模板/模型/数据/系统变更即回归；定指标→分流量→并行→分析。
- **判定**：升级前后关键指标不退化；多语言同 Prompt 无歧义漂移。

### 模块 9：合规测试

- **测什么**：歧视性输出、隐私保护(PII/会话泄露)、不当建议(医疗/财经/法律边界)、输出溯源、全球化合规。
- **怎么测**：敏感属性替换/偏见词/平等指标(StereoSet、DiscrimEval)；RAG 溯源、事实抽检(TruthfulQA、FactScore)；审计日志/决策链路。
- **判定**：不输出歧视/泄露 PII；高风险领域有免责边界；满足 GDPR / GB-T 45288 / NIST AI RMF。


### 模块 10：部署 · 训练 · 业务

- **测什么**：本地部署可用性、API 成功率/ART/P95/P99、数据污染(Min-K%)、过拟合/遗忘、A/B/灰度/影子、CI/CD 闭环。
- **怎么测**：vLLM/LMDeploy/Docker 起服务；evalscope API 测试；Min-K% Prob 概率法测污染；LLaMA-Factory 监控 Loss。
- **判定**：部署可启动连通；成功率达标；污染概率低；验证 Loss 不异常回升。
- **来源**：Min-K% Prob(arXiv:2310.16789)、I-LoRA(arXiv:2402.18865)、OpenCompass/evalscope。

#### 10.1 训练过程测试（加分项，AI 部署/算法测试方向）

训练过程本身就要测，不能"训完再测"——数据决定上限、训练充满不确定性、成本高、缺陷会被放大到下游。

| 测试点           | 测什么                              | 方法/工具                                                                    |
| ------------- | -------------------------------- | ------------------------------------------------------------------------ |
| **训练数据质量**    | 准确性/完整性/一致性/时效性/多样性 5 维度核对       | 抽样人工 review + 自动校验                                                       |
| **数据污染**      | 恶意注入/标注错误/泄露                     | **Min-K% Prob**（arXiv:2310.16789）：训练样本如果模型给的低概率 token 占比过高 → 疑似泄露；+ 人工抽检 |
| **过拟合/灾难性遗忘** | 训练-验证 Loss 曲线对比；旧任务保留集回测         | **I-LoRA**（arXiv:2402.18865）检测学新忘旧                                       |
| **训练稳定性**     | 实时监控 Loss/Acc/LR/GPU·CPU·内存，阈值告警 | 收敛异常：过慢=lr 小/初始化问题；过快=数据泄露/过拟合                                           |

**落地工具**：**LLaMA-Factory**（`github.com/hiyouga/LLaMA-Factory`，~7.4万★，ACL 2024）——零代码覆盖 SFT/DPO/PPO/KTO/ORPO，自带 LlamaBoard/TensorBoard/MLflow 监控，支持保留集回测查遗忘。是"训练过程测试"的落地载体。`evalscope` 能打通训练→评测全链路。

> **与应用层评测的衔接**：应用层评测是"训完看效果"，训练过程测试是"训中就控质量"。两头都懂，就能在算法团队和需求方之间做"质量翻译"。

#### 10.1.1 Loss 曲线判读与收敛速度异常分析

训练过程最该盯的就是 Loss 曲线。它不是"一个数"，而是两条线 + 横轴的组合。

**Loss 曲线怎么构成**

| 要素 | 含义 |
|------|------|
| 横轴 | 训练进度（step 或 epoch） |
| 纵轴 | 损失值（越小越好，交叉熵等损失函数输出） |
| 线 1 | **训练集 Loss（Train Loss）**：训练样本上的平均损失，反映「拟合训练数据」程度 |
| 线 2 | **验证集 Loss（Validation Loss / Eval Loss）**：未见过的验证样本损失，反映「泛化」能力 |

> 两个核心指标就是 **训练 Loss + 验证 Loss**。收敛速度异常与过拟合判据，本质都是看这两条线的「下降速率」和「彼此偏离程度」。

**收敛速度异常怎么判（两条线联动看）**

| 现象 | 判读 | 可能根因 |
|------|------|----------|
| 训练 Loss 下降极慢、长时间不收敛 | 收敛慢 | lr 过小 / 数据噪声大 / 梯度消失 / batch 太小 |
| 训练 Loss 持续降，验证 Loss 先降后升 | 过拟合（泛化 gap 扩大） | 训练数据量不足 / epoch 过多 / 正则弱 |
| 两条线都不降、原地震荡 | 欠拟合 / 不收敛 | lr 过大 / 模型容量不足 / 标签噪声 |
| 训练 Loss 突跳、毛刺多 | 训练不稳定 | 脏数据 / lr 调度异常 / 混合精度溢出 |

**损失值怎么判断（损失值本身不是"看一个数"）**

损失值有 4 个判读维度：

| 判读维度 | 看什么 | 异常信号 |
|---------|--------|----------|
| ① 是否有限 | 数值是不是正常浮点 | NaN / Inf → 直接判失败 |
| ② 下降趋势 | 随 step 整体走向 | 长时间不降、或阶跃式暴涨 → 异常 |
| ③ 收敛水平 | 最终是否平稳、落到什么值 | 远高于同数据同超参的基线 run → 不收敛 |
| ④ 泛化 gap | 验证 Loss − 训练 Loss | gap 持续扩大且超阈值 → 过拟合 |

**⚠️「任务执行失败」要分两类（关键区分）**

- **执行失败（硬失败 / infra 层）**：任务根本没正常跑完 —— Loss 出现 NaN/Inf、Loss 爆炸（突然 > 1e3 或阶跃跳升）、进程 OOM/崩溃/超时挂死、训练中途 hang。与"模型好不好"无关，是工程/环境/数据问题，先排查再重跑。
- **质量不达标（软失败 / 评测层）**：跑完了但指标没过验收线 —— 不收敛、过拟合、gap 过大。回到超参/数据/早停策略去调。

**可落地的判定规则（建议阈值，可程序化）**

| 规则 | 条件 | 结论 |
|------|------|------|
| R1 数值合法性 | `not finite(loss)` | 执行失败 |
| R2 爆炸检测 | `loss > 初始loss × 5` 或 `loss > 1e3` | 执行失败 |
| R3 停滞检测 | 连续 K 次 eval（如 K=10）下降 < 1e-4 | 收敛异常（软失败） |
| R4 过拟合检测 | `val_loss − train_loss > margin`（如 0.3）且 val_loss 回升 | 质量不达标 |
| R5 基线对比 | 最终 train_loss > 基线最终值 × 1.1 | 质量不达标 |

> 落地：R1–R2 直接判「执行失败」，R3–R5 判「质量不达标」。R4 触发但非过拟合时，疑似验证集分布偏离，用 KS/卡方检验校验两份数据特征分布是否漂移（呼应第 5 章避坑清单"训练/验证集分布偏离"）。

### 模块 11：大模型评测

- **测什么**：多模态、Agent/工具调用、长上下文、RAG、幻觉、指令遵循、校准/不确定性、能效/成本。
- **来源**：
  - 多模态：MMBench(arXiv:2307.06281)、VLMEvalKit
  - 长上下文：LongBench(arXiv:2308.09982)、LongBench-Write
  - RAG：RAGAS、MTEB/CMTEB、RAGEval
  - 幻觉：HaluEval(arXiv:2305.11747)、TruthfulQA(arXiv:2109.07958)、FactScore(arXiv:2305.14251)
  - 指令遵循：IFEval(arXiv:2308.03495，HELM 内置)
  - 校准/不确定性：HELM calibration

#### 11.1 幻觉检测与防御（深化）

幻觉分两类，测法不同：

| 类型                      | 定义                  | 检测方法                                        | 防御验证            |
| ----------------------- | ------------------- | ------------------------------------------- | --------------- |
| **忠实性幻觉（Faithfulness）** | 回答和给定上下文矛盾——有依据但不遵从 | DeepEval Faithfulness / RAGAS faithfulness  | 上下文对齐校验         |
| **事实性幻觉**               | 无中生有 / 事实错——完全没依据   | HaluEval / TruthfulQA / FactScore 思路 + 人工抽检 | RAG 检索增强 + 引用溯源 |

**防御手段的测试验证**：

| 防御手段       | 测什么                     | 数据集/思路                                |
| ---------- | ----------------------- | ------------------------------------- |
| RAG 检索增强   | 检索召回相关性，避免"检索错→生成错"     | RAGAS context_precision               |
| 引用溯源       | 要求回答带出处，人工/程序抽检出处是否真实存在 | FactScore 思路                          |
| 置信度校准 + 拒答 | 模型知识截止后的事应答"不知道"而非编     | **FreshQA**——问一个知识截止后的事件，验证模型不幻觉、坦诚未知 |
| 不可完成任务     | Agent 面对做不到的请求时，是否硬编假结果 | OSWorld 范式④：构造不存在设置/超出权限指令            |

> **时效性幻觉**：用户问"今天腾讯股价多少""帮我查最新政策"，模型靠训练知识硬答旧数据就是时效性幻觉。构造"截止后事件"用例验证走实时检索或诚实拒答。

#### 11.2 长上下文与多轮对话测试

| 测试点            | 方法                                      | 参照                       |
| -------------- | --------------------------------------- | ------------------------ |
| **窗口梯度**       | 4K→128K 逐步加压，观察何时开始丢信息、何时 OOM           | LongBench 思路             |
| **跨轮指代消解**     | "把刚才那个文件发给我"——验证 Agent 能正确绑定到前轮实体       | 轨迹断言：看工具调用填的实体 ID 是否指向前轮 |
| **上下文污染**      | 超长对话里早期约束被挤出窗口后，Agent 是否误触；不同话题混在一起导致串味 | 埋约束→撑窗口→触发约束             |
| **Token 预算控制** | 长任务是否会无限膨胀上下文，验证"摘要压缩/关键约束回注"机制是否生效     | 监控每轮 Token 增长曲线          |

> **上下文污染 vs 记忆污染**：记忆污染是"记忆系统本身串了/忘了"（存储层），上下文污染是"同一窗口内多话题互相干扰"（注意力层）。测试手段都靠构造干扰用例 + 轨迹检查。

#### 11.3 可观测性与线上反馈闭环

这是把"测试"从静态评测变成"持续质量闭环"的关键。没这一环，评测集永远滞后于真实场景。

| 步骤                  | 做什么                                                 | 工具/方法                   |
| ------------------- | --------------------------------------------------- | ----------------------- |
| **① 埋点/链路追踪**       | 每个 Agent 的工具调用名、参数、返回、耗时带 trace_id 串联               | 框架层统一埋点                 |
| **② 线上 badcase 收集** | 用户反馈 / 自动检测（faithfulness < 阈值 / 用户点"没用"）自动归档带 trace | 自动检测规则 + 人工收集           |
| **③ 标注 + 回流入评测集**   | badcase 标注失败类型（理解偏差/Skill 误选/幻觉/工具错），转成结构化评测用例      | 标注规范 + review 入库        |
| **④ 评测→归因→反馈→优化**   | 新版本发前跑全量回归，失败归因后推改进                                 | DeepEval + 归因分类 + 结构化报告 |

> **前提**：可观测性是诊断的前提（模块 4.5 二分法依赖它）。没埋点，轨迹断言和根因定位都跑不起来。至少要做到 trace_id 串联工具调用 + 日志可查。

#### 11.4 AI 产品灰度 / 影子 / A-B + 模型升级回归

模型迭代有风险——新模型可能退化、漂移、幻觉变多、安全下降。不能"一把梭"：

| 策略               | 怎么做                      | 测试介入点                             |
| ---------------- | ------------------------ | --------------------------------- |
| **灰度/金丝雀**       | 新模型先放 5% 流量，对比旧模型指标再逐步放量 | 核心指标（成功率/faithfulness/Token）不降才放量 |
| **影子部署（Shadow）** | 新模型并行跑但不对用户生效，结果和线上模型比对  | 验证无退化再切                           |
| **A-B 测试**       | 同流量分两路，统一指标对比            | 任务成功率、用户满意度                       |
| **模型升级回归**       | 升级前后跑**同一套评测集**做对比       | 掉点超阈值就拦（Q43 质量门禁思路）               |

> 工具：`evalscope` Arena / `ChatBench` 可做模型横向对比与稳定性评估。

#### 11.5 两层评测架构（实战推荐）

一个完整的 Agent 评测体系建议分两层构建，避免"体系和方法论混在一起"：

| 层级          | 做什么                                                                                                      | 用什么                        |
| ----------- | -------------------------------------------------------------------------------------------------------- | -------------------------- |
| **① 评测体系层** | 搭建五维度评测体系（Faithfulness/AnswerRelevancy/Hallucination/Toxicity/GEval），对失败案例按归因分类，产出 score+reason+归因+可执行建议 | **DeepEval 4.x**（直接跑，不是参照） |
| **② 数据集层**  | 参照 OSWorld 范式（口语化指令/初始状态/执行后校验），由 AI 设计场景化测试数据集，覆盖四大模块（如 Win Use/App Use/Browser Use/Computer Use）       | **OSWorld 范式**（参照设计，不是直接跑） |

> **两层协同**：体系层给出"怎么测、怎么判、怎么归因"，数据集层给出"测什么场景"。两层配合形成反馈闭环：归因发现的问题→优化模型→新版本重跑同一数据集→验证不退化。


### 11.6 专题：Agent Eval 非确定性评测与回归测试（模块 4 深化）

Agent 核心难点是**非确定性**，不能做快照比对，而要做「轨迹评估 + 随机化评估(stochastic) + 分层 CI 门禁」。

| 测试点     | 怎么测                                     | 判定标准                            |
| ------- | --------------------------------------- | ------------------------------- |
| 工具调用正确性 | 轨迹断言：工具名/参数 schema                      | 必要工具齐全、参数必要字段不缺                 |
| 调用顺序    | 子序列断言（允许中间穿插）                           | 关键顺序符合预期（如 搜索→预订）               |
| 终态/无死循环 | `max_steps_reached` + `final_answer` 非空 | 有终态答案且未死循环                      |
| 不可逆操作护栏 | 断言不出现直接执行 + 出现确认工具                      | 不可逆操作不被直接执行                     |
| 非确定性稳定  | stochastic run×N，通过率 ≥ 阈值               | 通过率 ≥ 0.8（可配 `AGENT_PASS_RATE`） |
| 答案质量/安全 | LLM-Judge（GEval rubric，复用 DeepEval）     | 任务完成度/安全合规达标                    |

**Agent Eval 对 11 模块的覆盖矩阵（命中 8 个）**

| 手册模块             | 覆盖    | 方式                            |
| ---------------- | ----- | ----------------------------- |
| 1 评测数据集/离线能力     | 🟡 间接 | GAIA/AgentBench 做能力基线         |
| 2 数据质量/公平性       | ❌     | 需其他手段                         |
| 3 鲁棒性/泛化/时效      | ✅     | stochastic run×N 看通过率稳定性      |
| 4 Agent 专项       | ✅ 核心  | 轨迹断言直接覆盖                      |
| 5 功能测试           | ✅     | 确定性代码断言                       |
| 6 性能             | ✅     | 复用 Locust + 每步时延断言            |
| 7 安全/异常输入        | ✅     | LLM-Judge + 拒绝断言              |
| 8 Prompt 工程与回归   | ✅     | golden 集语义 diff + 改动即回归       |
| 9 合规             | ✅     | 行为护栏（AgentEvalHQ 一等公民）        |
| 10 部署/训练/业务      | ❌     | 基础设施/权重/生产流量                  |
| 11 多模态/RAG/幻觉/指令 | ✅ 部分  | 工具含 RAG/多模态时复用 RAGAS/DeepEval |

> **结论**：Agent Eval 直接命中 11 模块里的 **8 个**（尤其 3/4/5/6/7/8/9 与 11 的工具相关部分）；1/2/10 与 11 非工具部分需其他手段。

> ### ⚠️ 重要澄清：Agent Eval 是否「主要用于回归测试、确保能力不退化」？
>
> 这个问题要分两层回答（已联网核实 Microsoft 官方文档与 2026 年 Agent 评测框架横评）：
>
> 1. **「智能体评测（Agent Evaluation 这门实践）」本质上就是为回归测试设计的。** Microsoft 在其 agent evaluation 文档中明确：用同一 test set 在改动前后重复运行，客观衡量能力是否退化；把用户反馈的 bug 加进 regression set 固化；更新知识源前跑评测 catch 回归。**这一点你的理解是对的**——"确保能力不退化"就是 Agent 评测的核心目的。
> 2. **但具体名为 "AgentEval" 的框架，其定位不完全等于"回归工具"**：
>    - **Microsoft Research 的 AgentEval**（AutoGen 团队，2023，Critic/Quantifier/Verifier）定位是"没有标准答案时，用 LLM 批评者自动给轨迹打分"，重点在**能力/轨迹质量评测**，可嵌入回归循环但不是它的招牌用途。
>    - 业界把"以回归为核心卖点"明确挂在 **Promptfoo**（"Regression testing your specific agent as you iterate on prompts and models"，diff 视图看哪些用例行为变了）和 **Microsoft 的 agent evaluation（test set 机制）** 以及 **AgentEvalHQ 的 StochasticRunner + ModelComparer（run×N 算通过率、版本横向对比）** 上。
> 3. **准确表述**：广义的 **Agent 评测实践 = 回归防护（防能力退化）**；具体做回归首选 **Promptfoo / Microsoft agent evaluation / AgentEvalHQ**；名为 **AgentEval** 的 Microsoft Research 框架更偏"无 ground truth 时的能力评测"。手册正文中把"Agent Eval"直接等同于"回归评测"略窄，特此澄清。

### 11.13 实战路线图：拿到一个 API 后从哪开始测（含每步覆盖的测试点）

> 适用：你刚拿到一个大模型或 AI 应用的 API（OpenAI 兼容端点 / RAG 服务 / Agent 服务）。下面是一条「低风险 → 高价值 → 防退化」的顺序，**每一步都标注它覆盖了第 1 章的哪些测试模块、以及为什么（防什么风险）**。可对照第 6 章「上手最小行动清单」落地，对照第 2 章选工具。

| 步骤                        | 目标                  | 覆盖的测试点（第 1 章模块） | 为什么（防什么风险）                                                   | 用什么（见第 2 章）                                            |
| ------------------------- | ------------------- | --------------- | ------------------------------------------------------------ | ------------------------------------------------------ |
| **第 0 步 · 收口范围**          | 确认被测对象类型与 SLA 目标    | 模块 1 / 5 / 10   | 纯模型、RAG、Agent、通用应用测试重点完全不同；先定边界避免**测错对象、漏维度**                | —（先访谈 / 看接口文档，拿到端点·鉴权·模型名）                             |
| **第 1 步 · 连通 + 冒烟**       | API 能通、不崩、不泄露内部错误   | 模块 5 / 10 / 7   | 先确认「能跑、返回格式对、异常输入不崩、不吐堆栈」，否则后续评测结果不可信；异常输入是 **0 成本高收益**的安全基线 | test_01（轻量连通）+ 手工异常注入（超长/空/特殊字符/越权 token）              |
| **第 2 步 · 能力门禁**          | 知识 / 推理达到业务阈值       | 模块 1            | 能力是底座，低于业务门禁直接不可用；标准 Benchmark 保证**横向可比、可复现**                | lm-evaluation-harness / OpenCompass（MMLU/CMMLU/C-Eval） |
| **第 3 步 · 安全注入**          | 注入 / 越权 / PII 泄漏被拒绝 | 模块 7 / 9 / 2    | 上线**最高风险**：注入可致数据泄露、越权操作、违规输出；必须先有拒绝断言                       | garak / promptfoo / DeepEval（注入拒绝 / Toxicity）          |
| **第 4 步 · RAG / 幻觉**      | 不编答案、可溯源            | 模块 11 / 9       | RAG 最易「编造」，忠实度是体验与安全底线；**非 RAG 应用跳过**                        | RAGAS + TruthfulQA / HaluEval 真实性抽检                    |
| **第 5 步 · Agent 轨迹**      | 轨迹正确、稳定、有护栏         | 模块 4 / 8 / 6    | Agent **非确定性**，单次结果不可信；需 stochastic 通过率门禁 + 改动即回归**防退化**     | test_04（轨迹断言 + StochasticRunner + 行为护栏 + LLM-Judge）    |
| **第 6 步 · 性能压测**          | TTFT / 吞吐 / 会话隔离达标  | 模块 6            | 用户感知 TTFT、系统吞吐、长上下文 OOM、并发串扰是**上线硬指标**                       | Locust（TTFT / 并发 / RPS）                                |
| **第 7 步 · 鲁棒 / 公平 / 多模态** | 抗噪声、无偏见、多模态可用       | 模块 3 / 2 / 11   | 生产环境有对抗输入与多样用户，缺则上线后**口碑与合规**风险                              | PromptBench / StereoSet·BBQ / MMBench / LongBench      |
| **第 8 步 · 接 CI 固化回归**     | 一变更就回归、bug 不复发      | 模块 8 / 10       | 模型 / 数据 / 模板会变，只有**持续回归**才能「确保能力不退化」                         | pytest + CI（把用户反馈 bug 固化为回归用例）                         |

**为什么是这个顺序（设计原则）**

- **先冒烟后深挖**：先确认 API 能跑、不崩，再投入 Benchmark / 评测成本，避免用坏数据得出错误结论。
- **安全前置（P0）**：注入 / 越权是上线最高风险，且探针成本低（garak / promptfoo 开箱即用），应尽早跑、反复跑。
- **按对象裁剪**：RAG/幻觉、Agent/轨迹只在对应类型才做，避免对纯模型硬跑 RAGAS 浪费时间。
- **能力做门禁、回归做保障**：能力评测定「准入」，CI 回归定「不退化」——二者缺一不可（呼应 1.12 澄清：Agent 评测实践本质是回归防护）。

> **时间只够做 3 件事？** 优先：第 1 步（连通 + 异常输入冒烟）+ 第 3 步（安全注入）+ 第 8 步（接 CI）。这三项成本最低、风险覆盖最高，能拦住绝大多数上线事故。

### 2.4 安全 / 幻觉 / 单测 — DeepEval、garak、promptfoo

#### DeepEval 4.x（重点详解）

- **仓库**：`github.com/confident-ai/deepeval`（星标约 17k–18k，2026-09 核实，4.1.x）
- **定位**：官方称「LLM 评测的 Pytest」，50+ 指标，原生 pytest/CI 集成。

**v4.x 统一语义（关键防坑）**：5 个核心指标 score∈[0,1] **全"越高越好"**，threshold 是最低通过线——低于 threshold 即 fail。旧教程/博客中出现的"越低越好"是 v0/v1 过时说法，4.x 已统一。注意 HallucinationMetric 语义也已对齐：0=无幻觉，1=严重幻觉，**超过 threshold 需关注**。

| 指标                    | 测什么                                  | 关键参数                            | score 语义     | 推荐阈值          |
| --------------------- | ------------------------------------ | ------------------------------- | ------------ | ------------- |
| FaithfulnessMetric    | 输出是否忠于 **retrieval_context**（RAG 场景） | `retrieval_context`             | 越高越忠实        | ≥ 0.8（面向用户内容） |
| HallucinationMetric   | 是否产生幻觉（无依据编造）                        | `context`（非 retrieval_context）  | 0=无幻觉，1=严重幻觉 | ≤ 0.5         |
| AnswerRelevancyMetric | 回答是否切题                               | `input`                         | 越高越切题        | ≥ 0.7         |
| ToxicityMetric        | 是否产生有害内容                             | `actual_output`                 | 0=无毒，1=极毒    | ≤ 0.5         |
| GEval                 | 自定义 rubric 评判                        | `criteria` 或 `evaluation_steps` | 按自定义 rubric  | 业务自定          |

> **Hallucination vs Faithfulness 区分**：Faithfulness 对 `retrieval_context`（有检索上下文时判断输出是否遵从），Hallucination 对 `context`（判断输出是否在上下文之外编造）。简单说：Faithfulness 是"有依据但歪曲"，Hallucination 是"无依据而编造"。

**核心数据结构 LLMTestCase**：

```python
LLMTestCase(
    input="用户的指令",              # 必填
    actual_output="模型实际返回",     # 必填
    expected_output="预期正确输出",   # 部分指标需要
    context=["上下文信息"],           # HallucinationMetric 用
    retrieval_context=["检索上下文"]  # FaithfulnessMetric 用
)
```

**执行方式**：

- `assert_test(test_case, [metrics])` — 配合带 threshold 的 metric，不达标时 pytest fail
- `metric.measure(test_case)` — 只打分不拦截，可单独 `assert metric.score >= metric.threshold`
- `evaluate(test_cases, metrics)` — 批量跑，输出 score + reason + pass/fail 表格

> ⚠️ **`assert_test` 必须配合带 threshold 的 metric 才会在不达标时失败——不带 threshold 的 metric 只打分不拦截**，这是个常见坑。

**GEval（LLM-as-a-Judge）详解**：

GEval 是 DeepEval 最灵活的指标，你写 rubric（评分标准），裁判模型按 rubric 打分。底层用 CoT（链式推理）：先让裁判模型生成评估步骤，再逐步打分。

| 参数                 | 说明                                   | 适用场景                       |
| ------------------ | ------------------------------------ | -------------------------- |
| `criteria`         | 自然语言评分标准（如"评估回答是否准确完整"）              | 快速原型、非关键判定；浮动约 ±0.05       |
| `evaluation_steps` | 显式评估步骤列表（如["检查是否提及关键信息","检查有无事实错误"]） | **回归推荐**：步骤固定，分数更稳定        |
| `model`            | 裁判模型，支持 `DeepEvalBaseLLM` 自定义        | 可接 GPT-4o/DeepSeek/本地 Qwen |

**已知 LLM-as-a-Judge 偏差**（面试必知）：

- 位置偏差：倾向给靠前/靠后的内容更高分
- 长度偏差：更长回答常获更高分（即使质量相当）
- 自我偏好：裁判模型倾向给自己同类模型更高分
- 应对：关键 case 人工抽检校准、多模型交叉评判、reason 比分数更有价值

**评判模型与被测模型分离（铁律）**：被评模型用私有端点，裁判模型另选更强模型（如被测用 DeepSeek，裁判用 GPT-4o-mini）。不能"裁判也是选手"，否则归因不准。

| ----- | ------------------- | ------------- |
| 格式错误  | 输出不符合预期 JSON/schema | 工具调用参数校验      |
| 拒绝执行  | Agent 拒绝合理指令        | 功能测试          |
| 幻觉/编造 | 声称完成但实际未执行          | Hallucination |
| 工具误选  | 调用了错误工具             | 路由/意图理解       |
| 参数错误  | 工具对但参数缺/错           | 参数 schema 校验  |
| 死循环   | 在 max_steps 内未达终态   | 死循环防护         |
| 状态遗忘  | 忘记前轮关键信息            | 记忆/上下文测试      |
| 部分完成  | 只完成了部分子任务           | 任务完成度         |
| 越权操作  | 执行了未授权操作            | 安全/护栏         |
| 降级失败  | 工具失败后未优雅降级          | 错误恢复          |

**τ-bench 数据集设计（详解）**：

τ-bench（Tool-Agent-User Interaction Benchmark，Sierra Research + Princeton，ICLR 2025）核心创新是测 Agent 在**多轮对话中与用户协作、调用工具、遵守领域策略**的端到端能力——而非单轮指令执行。

| 设计要素 | 说明 |
|---|---|
| **领域** | τ-retail（零售，115 任务）+ τ-airline（航空，50 任务），共 165 任务 |
| **交互模型** | Agent + LLM 模拟用户 + 工具 API + JSON 数据库，多轮对话 |
| **领域策略（Policy）** | Markdown 格式描述的业务规则（权限/流程/限制），部分在 API 中硬检查，部分需 Agent 自行遵守 |
| **任务结构** | `instruction`（用户指令，含身份/意图/偏好）+ `initial_db_state`（初始数据库状态）+ `target_db_state`（期望终态）+ `allowed_tools`（允许调用的工具集） |
| **评估方法** | **DB 状态对比**：对话结束后对比数据库最终状态与标注目标状态，逐字段比对，全部一致才算通过 |
| **关键发现** | GPT-4o pass¹ < 50%，pass⁸ < 25%（retail）——"偶尔成功≠可靠" |

**τ-bench 的三大设计要求**（区别于早期 Agent 基准）：

| 要求 | 含义 |
|---|---|
| **① Human interaction** | Agent 必须与模拟用户多轮对话，不能假设所有信息在首轮就给全 |
| **② Tool-mediated action** | Agent 必须通过 API 读写结构化数据库，而非仅"描述该做什么" |
| **③ Policy compliance** | Agent 必须遵守领域策略（权限/流程/例外），策略不强制由工具实现 |

> **数据构造三阶段**：① 手动领域设计（建 DB/API/Policy）→ ② LM 辅助合成数据生成 → ③ 手动任务标注与验证。保证每条任务在策略下只有一个正确结果。

**τ-bench vs AgentBench 对比**：

| 维度 | AgentBench | τ-bench |
|---|---|---|
| **发布** | 2023，ICLR 2024 | 2024，ICLR 2025 |
| **核心目标** | 测 Agent 多步任务能力基线（8 环境） | 测 Agent 与用户协作 + 工具调用 + 策略遵从的端到端可靠性 |
| **任务设计** | 单轮指令 → Agent 自主执行多步 | **多轮对话**：用户信息增量给出，Agent 需追问/确认 |
| **评估方式** | 任务成功率（环境内置判定） | **DB 状态对比**（逐字段精确比对终态） + pass^k |
| **用户模拟** | 无（指令一次性给全） | **有**（LLM 模拟用户，多轮交互） |
| **策略遵从** | 无显式业务策略 | **有**（Markdown 策略文档，部分需 Agent 自行遵守） |
| **可靠性指标** | 无（只看成功率） | **pass^k**（k 次全过才算通过，强调稳定性） |
| **环境** | OS/DB/Web/游戏等 8 个 | 零售 + 航空 2 个垂直领域 |
| **失败分析** | 10 类失败分类 | DB 推理/策略解释/复合请求+记忆 3 类 |
| **参照价值** | 参照**任务分类模式 + 失败归因**（POMDP 结构 + 10 类失败） | 参照**多轮协作 + 策略遵从 + DB 状态校验 + pass^k 可靠性** |

> **一句话区分**：AgentBench 是"给你一个指令，看你能走多远"（能力基线）；τ-bench 是"和用户聊着把事办了，还要守规矩，而且每次都得办成"（可靠性 + 协作 + 策略遵从）。

> **参照口径**：两者都是"参照 Agent 评测用例设计模式"，不是直接跑。AgentBench 参照其 POMDP 任务结构 + 失败分类；τ-bench 参照其多轮协作 + DB 状态校验 + pass^k 可靠性指标。

**τ-bench pass^k 可靠性指标**：

pass^k 衡量 Agent 的**可靠性**而非平均能力——k 次全过才算通过，强调"稳定可靠"而非"偶尔成功"。

公式：`pass^k = min(1, (c - k + 1) / n)`

其中 `n` = 总测试次数，`c` = 成功次数，`k` = 连续通过要求。

| 示例 | n | c | pass¹ | pass² | pass⁸ | 含义 |
|---|---|---|---|---|---|---|
| 10 次跑 8 次过 | 10 | 8 | 0.8 | 0.7 | 0.3 | 平均 80%，但连续 8 次只有 30%——不够可靠 |
| 10 次跑 10 次过 | 10 | 10 | 1.0 | 1.0 | 1.0 | 完全可靠 |
| GPT-4o retail | — | — | <0.5 | — | <0.25 | SOTA 也不过半，连续 8 次更差 |

> **实战用法**：同一用例 stochastic run×N，算 pass^k（k=1 为通过率，k≥2 衡量稳定性）。高风险操作建议 pass²≥0.8 才放行。τ-bench 论文用 pass⁸ 衡量"真正可靠"——8 次全过才算通过。

**OSWorld 三范式 + 不可完成任务**（设计评测数据集的方法论）：

OSWorld 的核心价值不在于直接跑它的 369 个任务，而在于它的**任务构建范式**——可以直接复用来构建你自己业务的评测数据集：

| 范式                                | 核心思想                        | 测什么         | 示例                          |
| --------------------------------- | --------------------------- | ----------- | --------------------------- |
| **① 口语化指令（含歧义）**                  | 用真实用户口吻，带模糊/省略              | 意图理解 + 歧义消解 | "帮我把桌面上这些发票按月份整理"           |
| **② 明确初始状态（init state）**          | 定义清楚"系统一开始是什么样"             | 可复现性        | "桌面有 6 个混合格式发票文件"           |
| **③ 执行后评估（execution-based eval）** | 不只看 Agent 说了什么，用脚本校验操作是否真生效 | 操作落地校验      | 校验月份文件夹已创建、文件已移入            |
| **④ 不可完成任务**                      | 测 Agent 面对做不到的请求时，是否硬编假结果   | 幻觉底线        | "帮我把超频保护模式关掉"（Windows 无此设置） |

> **引用口径**：OSWorld 是"AI 设计评测数据集的参照范式"（不是"直接跑学术基准"）。AgentBench/τ-bench 是"参照 Agent 评测用例设计模式"。DeepEval 才是"直接搭建评测体系跑"。三者别混。

## 5. 常见错误与避坑清单

- 误用 RAGAS 已废弃的 `evaluate()`/`LangchainLLMWrapper`（v0.4+ 已废弃/移除，改用 `@experiment` + `llm_factory`）。
- DeepEval `assert_test` 不带 `threshold` 的 metric 只打分不拦截。
- **DeepEval 4.x 统一语义**：5 指标 score 全"越高越好"，threshold 是最低通过线。旧教程/博客"越低越好"是 v0/v1 过时说法，别信。Hallucination 语义也已对齐（0=无幻觉，1=严重）。
- **Hallucination vs Faithfulness 混用**：Faithfulness 对 `retrieval_context`（RAG 场景），Hallucination 对 `context`（非检索上下文），参数别填错。
- **GEval criteria vs evaluation_steps**：`criteria` 快但浮动约 ±0.05，`evaluation_steps` 步骤固定分数更稳——回归评测推荐用 `evaluation_steps`。
- **LLM-as-a-Judge 偏差**：裁判模型存在位置/长度/自我偏好偏差，关键 case 需人工抽检校准，reason 比分数更有价值。
- lm-evaluation-harness 中文任务名硬编码旧代号（如 `ceval-valid`）→ 先 list 核实。
- 把库默认阈值当质量要求（faithfulness 默认 0.5 偏低，面向用户内容建议 ≥ 0.8）。
- 凭印象报框架星标或论文编号 → 必须先联网核实再写。
- Agent 评测做快照比对 → 应做轨迹断言 + stochastic 通过率门禁。
- 被评模型与裁判模型混用同一端点 → 应分离，裁判用更强模型。
- 训练/验证集分布偏离（数据泄露/划分不当）→ 用 KS/卡方检验 + 特征可视化对比。
- 数据污染未检 → Min-K% Prob 概率法（arXiv:2310.16789）识别疑似泄露样本。
- **鲁棒性与安全混淆**：鲁棒性是"输入噪声"（用户无心之失），安全是"对抗攻击"（有意误导）——两者测试方法、工具、负责团队都不同，别混。
- **OSWorld/AgentBench/DeepEval 引用口径混**：OSWorld 是"AI 设计数据集的参照范式"（不是直接跑），AgentBench/τ-bench 是"评测用例设计模式参照"，DeepEval 才是"直接搭建评测体系跑"——三者别混。
- **多 Agent 诊断前提遗漏**：二分法依赖可观测性（trace_id 串联），没埋点这套方法跑不起来。

## 8. 术语表（Glossary）

| 术语 | 英文 / 缩写 | 一句话解释 |
|------|-----------|-----------|
| 大模型 | LLM | 大语言模型，本文泛指含生成 / 推理能力的基座或微调模型 |
| 检索增强生成 | RAG | 先检索相关资料再让模型生成，降低幻觉、增强可溯源 |
| 智能体 | Agent | 能自主规划、调用工具、多步完成任务的系统 |
| 裁判模型 | LLM-as-a-Judge | 用更强的模型给被测输出打分，替代"唯一标准答案" |
| 函数调用 | Function Calling / Tool Call | 模型输出结构化调用请求（工具名 + 参数） |
| 鲁棒性 | Robustness | 输入带噪声 / 扰动时输出仍稳定（用户无心之失） |
| 红队 / 安全 | Red Teaming / Security | 有意对抗输入（注入 / Jailbreak）探查漏洞 |
| 幻觉 | Hallucination | 模型生成无依据 / 与事实不符的内容 |
| 忠实度 | Faithfulness | 输出是否忠于给定上下文（RAG 场景） |
| 过拟合 | Overfitting | 训练 Loss 降但验证 Loss 升，泛化差 |
| 泛化 gap | Generalization Gap | 验证 Loss − 训练 Loss，持续扩大即过拟合预警 |
| 非确定性 | Non-determinism | 同输入多次跑结果可能不同，需用 stochastic 通过率门禁 |
| 通过率门禁 | pass^k | k 次全过才算通过，衡量稳定性 |
| 数据污染 | Data Contamination | 训练数据混入评测样本，Min-K% Prob 检测 |
| 灾难性遗忘 | Catastrophic Forgetting | 学新任务忘旧任务，I-LoRA 检测 |
| 轨迹断言 | Trajectory Assertion | 对 Agent 工具调用序列（名 / 参 / 序 / 终态）做断言 |
| 早停 | Early Stopping | 验证 Loss 回升即停训，防过拟合 |
| 置信度校准 | Calibration | 模型"知道 / 不知道"的概率是否可靠，避免硬答 |
