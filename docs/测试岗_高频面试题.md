# 自动化测试岗 · 高频面试题梳理

> 适用方向：自动化测试（功能/接口/性能自动化）  
> 说明：SQL 与网络是自动化测试的两条基础线——SQL 用于测试数据准备与结果校验，网络用于接口测试与问题定位。下面按「考点 → 高频题 → 测试场景」组织。

---

## 一、SQL 高频面试题

### 1.1 基础查询

| 考点             | 高频题                                      | 测试场景          |
| -------------- | ---------------------------------------- | ------------- |
| SELECT / WHERE | 查询某状态、某时间范围内的数据                          | 用例执行后校验落库数据   |
| 模糊查询           | `LIKE '%测试%'` 与 `_` 的区别                  | 校验含特定标识的测试数据  |
| 排序去重           | `ORDER BY` + `DISTINCT`                  | 校验返回列表顺序、去重逻辑 |
| 分页             | `LIMIT / OFFSET`（MySQL）、`ROWNUM`（Oracle） | 接口分页参数测试      |

**必会题**

1. 查询 `users` 表中 `age` 在 18~30 之间且 `city` 为 '深圳' 的用户。
2. `DISTINCT` 和 `GROUP BY` 去重有什么差别？
3. `LIMIT 10, 20` 代表什么含义？

```sql
SELECT * FROM users
WHERE age BETWEEN 18 AND 30
  AND city = '深圳'
ORDER BY created_at DESC
LIMIT 10 OFFSET 20;
```

**解析**
1. **Q1（见上 SQL）**：`BETWEEN 18 AND 30` 含边界；`AND` 多条件；`ORDER BY ... DESC` 降序；`LIMIT 10 OFFSET 20` = 跳过前 20 条取 10 条（第 21–30 条）。分页口诀：**OFFSET 是跳过数，LIMIT 是取几条**。
2. **Q2（DISTINCT vs GROUP BY）**：`DISTINCT` 仅去重、不能统计；`GROUP BY` 能分组并配合聚合（`COUNT/SUM`）统计每组数据。只去重单列两者都行，要统计必须用 `GROUP BY`。
3. **Q3（LIMIT 10, 20）**：MySQL 里 `LIMIT 10, 20` 等价于 `LIMIT 20 OFFSET 10`——**逗号前是 OFFSET（跳过），逗号后是 LIMIT（取）**，易记反，注意与 `LIMIT 10 OFFSET 20` 区分。

### 1.2 多表连接（JOIN）

| 类型         | 含义    | 测试注意点                   |
| ---------- | ----- | ----------------------- |
| INNER JOIN | 两表交集  | 关联字段为空时不返回              |
| LEFT JOIN  | 左表全保留 | 右表无匹配时右侧为 NULL          |
| RIGHT JOIN | 右表全保留 | 同上反向                    |
| FULL JOIN  | 全外连接  | MySQL 不直接支持，需用 UNION 模拟 |
| 自连接        | 表连接自身 | 上下级、树形结构                |

**必会题**

1. 查询「下过订单的用户及其订单数」（LEFT JOIN 防止漏掉 0 订单用户）。
2. `LEFT JOIN` 的过滤条件写在 `ON` 还是 `WHERE`？结果有何不同？→ 写在 `ON` 里保留左表全部，写在 `WHERE` 里会过滤掉 NULL 行。

```sql
SELECT u.id, u.name, COUNT(o.id) AS order_cnt
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;
```

**解析**
1. **Q1（见上 SQL）**：用 `LEFT JOIN` 保证「没下过单的用户」也出现在结果里（订单数计 0），若用 `INNER JOIN` 会漏掉这些人——正是测试时要验证「无数据时是否仍返回」的边界。
2. **Q2（ON vs WHERE 过滤）**：`LEFT JOIN ... ON 条件` 在**连接时就过滤右表**，左表记录始终保留（右表不匹配则补 NULL）；`WHERE 条件` 在**连接完成后**过滤整行，会把右表为 NULL 的左表记录也删掉。结论：**想保留左表全部 → 条件写 ON；想最终过滤 → 写 WHERE**。

### 1.3 子查询与集合

- **标量子查询**：返回单个值，可放 SELECT 中。
- **IN / NOT IN**：注意 `NULL` 陷阱（`NOT IN (NULL)` 永远为假）。
- **EXISTS / NOT EXISTS**：带关联，通常比 `NOT IN` 更安全高效。
- **UNION vs UNION ALL**：前者去重后者不去，性能差异大。

**必会题**

1. 查询「从未下过单」的用户（用 `NOT EXISTS` 或 `LEFT JOIN ... IS NULL`）。
2. `IN` 和 `EXISTS` 在什么场景下性能差异明显？

```sql
SELECT * FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);
```

**解析**
1. **Q1（见上 SQL）**：「从未下单」= 订单表里没有该用户。两种写法：① `NOT EXISTS`（关联子查询，遇到即停，效率高）；② `LEFT JOIN orders ... WHERE o.id IS NULL`。
2. **Q2（IN vs EXISTS 性能）**：子查询**结果集小、主表大**时，`EXISTS` 更高效（对主表每行只做一次判断，能用索引）；子查询结果集**大**时 `IN` 可能先物化大集合反而慢。口诀：**外表大用 EXISTS，内表小可用 IN**；且 `NOT IN` 遇 NULL 会全失败，必须用 `NOT EXISTS` 替代。

### 1.4 聚合与分组

| 函数                | 用途    | 测试注意                                     |
| ----------------- | ----- | ---------------------------------------- |
| COUNT / SUM / AVG | 统计    | `COUNT(*)` 含 NULL 行，`COUNT(col)` 不计 NULL |
| GROUP BY          | 分组    | SELECT 非聚合列必须出现在 GROUP BY                |
| HAVING            | 分组后过滤 | 与 WHERE 区别：HAVING 作用于聚合结果                |
| CASE WHEN         | 行内分支  | 测试多状态映射                                  |

**必会题**

1. 统计每个城市的用户数，只显示用户数 > 100 的城市。
2. `WHERE` 与 `HAVING` 的执行顺序区别？

```sql
SELECT city, COUNT(*) AS cnt
FROM users
GROUP BY city
HAVING COUNT(*) > 100;
```

**解析**
1. **Q1（见上 SQL）**：`GROUP BY city` 按城市分组，`COUNT(*)` 算每组人数，`HAVING COUNT(*) > 100` 在分组后筛掉人数 ≤100 的城市（`WHERE` 不能用聚合函数，故用 `HAVING`）。
2. **Q2（WHERE vs HAVING 执行顺序）**：`WHERE` 在**分组前**过滤单行（不能用聚合函数）；`HAVING` 在**分组后**过滤组（可用聚合函数）。顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY。性能上能放 WHERE 的尽量放 WHERE（先缩小数据量再分组）。

### 1.5 增删改（DML）与事务

- **INSERT / UPDATE / DELETE** 基本语法。
- **事务**：`BEGIN; ... COMMIT; / ROLLBACK;` → 自动化测试中用于「用例执行前准备数据、执行后回滚」保证用例隔离。
- **脏数据清理**：测试后 `DELETE` 或 `TRUNCATE`（`TRUNCATE` 不可回滚、自增重置）。

**名词解释与示例（事务 / 事务回滚）**
- **事务（Transaction）**：把一组 SQL 操作打包成一个"要么全成、要么全不成"的逻辑单元（ACID：原子性、一致性、隔离性、持久性）。
- **COMMIT（提交）**：事务内所有改动**真正生效**、落库。
- **ROLLBACK（回滚）**：撤销事务内所有改动，数据库恢复到 `BEGIN` 之前的状态——就像这组操作从没发生过。

基础示例（体会"要么全成要么全不成"）：
```sql
BEGIN;
UPDATE accounts SET balance = balance + 100 WHERE user_id = 1;  -- 改余额
INSERT INTO logs(user_id, change) VALUES (1, 100);             -- 写日志
ROLLBACK;   -- 撤销上面两步：余额和日志都复原，像没执行过
-- COMMIT;  -- 若一切正常，改成 COMMIT，改动才落库
```

测试中的用法（用例隔离，对应下方解析 Q1）：每条用例用 `BEGIN` 开头，结束（无论成功失败）在 `finally` 里 `ROLLBACK`，测试数据用完即丢，下条用例从干净环境开始，并发也不串扰：
```python
def test_create_order():
    db.execute("BEGIN")
    try:
        # 造数据、调接口、查库断言……
        assert order_created()
    finally:
        db.execute("ROLLBACK")   # 关键：无论断言成败都回滚，不留脏数据
```

**必会题**

1. 自动化测试中，如何保证两条用例之间的数据互不干扰？（事务回滚 / 独立测试库 / 数据 factory）
2. `DELETE` 与 `TRUNCATE` 的区别？

**解析**
1. **Q1（用例隔离）**：三种思路——① **事务回滚**：每条用例 `BEGIN`，结束 `ROLLBACK`，数据不留库；② **独立测试库/环境**：用例间互不影响；③ **数据工厂+唯一标识**：每条用例动态生成唯一前缀/随机 ID，避免冲突。核心是「**不依赖共享状态**」。
2. **Q2（DELETE vs TRUNCATE）**：`DELETE` 逐行删、可带 `WHERE`、可回滚、不重置自增；`TRUNCATE` 整表清空、速度快（释放数据页）、**不可回滚**、重置自增计数器、不能带条件。清理大量测试数据时用 `TRUNCATE` 更高效。

### 1.6 索引与性能

- **索引作用**：加速查询，但拖慢写入。
- **最左前缀原则**：联合索引 `(a,b,c)` 只有 `a` 命中才能用索引。
- **索引失效场景**：`LIKE '%xx'` 左模糊、对列做函数运算、隐式类型转换、`!=`、`OR` 不当。
- **执行计划**：`EXPLAIN` 看 `type`（ALL=全表扫描，需优化）、`rows`、`key`。

**必会题**

1. 什么情况下索引会失效？
2. 接口响应慢，如何用 SQL 层面定位？（`EXPLAIN` + 慢查询日志）

**解析**
1. **Q1（索引失效）**：常见场景——① 对索引列做函数/运算（`WHERE YEAR(created)=2026`）；② 左模糊 `LIKE '%xx'`；③ 隐式类型转换（字符串列传数字）；④ `!=`、`<>`、`NOT IN`、`IS NULL` 一定程度；⑤ 复合索引不满足**最左前缀**（`(a,b)` 只查 `b` 用不上）；⑥ `OR` 连接非索引列。
2. **Q2（慢 SQL 定位）**：① `EXPLAIN` 看 `type`（出现 `ALL`=全表扫描要优化）、`key`（实际用的索引）、`rows`（扫描行数）；② 开**慢查询日志**抓超时 SQL；③ 结合索引缺失/失效分析。接口慢先定位是 SQL 慢还是网络慢（抓包看 TTFB）。

### 1.7 测试专项：数据校验实战

自动化测试中 SQL 最常见的用法：

1. **接口测试后落库校验**：调用接口 → 查库断言字段值。

```sql
SELECT status, amount FROM orders WHERE order_no = 'TEST20260807';
```

1. **测试数据构造**：直接插库准备前置数据。
2. **数据一致性**：跨表/跨库核对（如订单与流水金额一致）。
3. **边界值**：空值、重复数据、超长字段的存储表现。

**必会题**

1. 接口自动化中，SQL 主要用在哪些测试环节？

**解析**
1. **Q1（SQL 在测试中的角色）**：① 前置造数（插库准备测试数据）② 后置校验（接口调完查库断言落库字段）③ 数据一致性核对（跨表/跨库金额、状态一致）④ 边界验证（NULL、重复、超长字段存储）。一句话：**SQL 是自动化测试的「数据眼睛」**。

## 二、网络相关高频面试题（自动化测试方向）

> 涵盖 HTTP/HTTPS、接口测试、抓包定位、安全基础，以及 WebSocket 实时通信专项。

### 2.1 网络基础

| 考点               | 高频题                  |
| ---------------- | -------------------- |
| OSI / TCP-IP 模型  | 七层 vs 四层，各层代表协议      |
| TCP 三次握手 / 四次挥手  | 为什么需要三次？TIME_WAIT 作用 |
| UDP vs TCP       | 区别与适用场景（直播用 UDP）     |
| DNS              | 域名解析过程，DNS 污染        |
| 浏览器输入 URL 到显示的过程 | 经典综合题                |

**必会题**

1. 简述 TCP 三次握手过程，为什么不是两次？
2. 从浏览器输入 URL 到页面展示，中间经历了什么？

**解析**
1. **Q1（三次握手）**：① SYN（客户端→服务端，seq=x）；② SYN+ACK（服务端→客户端，seq=y, ack=x+1）；③ ACK（客户端→服务端，ack=y+1），连接建立。**为什么不是两次**：两次无法确认「客户端的接收能力」与「服务端的发送能力」，且会导致**历史重复连接**被误建。三次已双向确认，第四次多余。
2. **Q2（URL→页面）**：DNS 解析域名→IP → 建立 TCP 连接（三次握手）→ 发 HTTP 请求 → 服务端响应（状态码+HTML）→ 浏览器解析渲染（构建 DOM/CSSOM→渲染树→绘制）→ 加载子资源（JS/CSS/图片）。补充：HTTPS 还需 TLS 握手。

---

### 2.2 HTTP / HTTPS（接口测试核心）

| 考点                | 高频题 / 要点                             |
| ----------------- | ------------------------------------ |
| 请求结构              | 请求行 + 请求头 + 空行 + 请求体                 |
| 响应结构              | 状态行 + 响应头 + 响应体                      |
| 请求方法              | GET/POST/PUT/DELETE/PATCH 语义         |
| 状态码               | 2xx 成功 / 3xx 重定向 / 4xx 客户端 / 5xx 服务端 |
| GET vs POST       | 参数位置、幂等性、缓存、安全性                      |
| HTTPS             | SSL/TLS 握手、对称/非对称加密结合                |
| Cookie vs Session | 存储位置、关联方式、Token 替代                   |

**必会题**

1. 常见状态码含义：`200 / 201 / 301 / 302 / 400 / 401 / 403 / 404 / 500 / 502 / 503`？
2. GET 和 POST 的本质区别是什么？（不止参数位置）
3. HTTPS 如何保证安全？能防中间人攻击吗？
4. Cookie、Session、Token 的区别与适用场景？

**解析**
1. **Q1（状态码）**：`200` 成功；`201` 创建成功；`301` 永久重定向；`302` 临时重定向；`400` 请求参数错误；`401` 未认证（未登录）；`403` 无权限（forbidden）；`404` 资源不存在；`500` 服务端内部错误；`502` 网关错误（后端无响应/代理收不到）；`503` 服务不可用（过载/维护）。**常考 401 vs 403**：401「你谁啊没登录」，403「知道你是谁但没权限」。
2. **Q2（GET vs POST 本质）**：本质在**语义与幂等性**——GET「获取资源」、幂等、可缓存、参数在 URL；POST「提交/创建」、非幂等、参数在 body、更安全。参数位置只是表现。GET 受 URL 长度限制，POST 无。
3. **Q3（HTTPS 安全）**：HTTPS = HTTP + TLS，用**非对称加密**协商出**对称密钥**，之后用**对称加密**传数据（兼顾安全与性能）。能防窃听/篡改，但**不能防「中间人伪造证书」**——需客户端校验证书链（CA 信任）才真正安全。
4. **Q4（Cookie/Session/Token）**：`Cookie` 存**客户端**浏览器，随请求自动带；`Session` 存**服务端**，靠 Cookie 里的 sessionId 关联；`Token`（如 JWT）无状态、自包含、客户端存本地、请求头携带（`Authorization: Bearer`）。前后端分离/分布式多用 Token。

### 2.3 接口测试（自动化测试重点）

| 考点     | 高频题                                |
| ------ | ---------------------------------- |
| 接口测试流程 | 需求分析 → 用例设计 → 脚本编写 → 执行 → 报告       |
| 用例设计维度 | 功能、参数边界、异常、安全、性能                   |
| 鉴权方式   | Basic / Bearer Token / OAuth2 / 签名 |
| 参数化    | CSV / JSON / 环境变量驱动                |
| 断言     | 状态码、响应体字段、响应时间、Schema              |
| 关联     | 上一个接口返回值提取给下一个（正则 / JSON Path）     |

**必会题**

1. 接口测试一般校验哪些内容？
2. 如何处理接口之间的数据依赖（如登录 token 传给后续接口）？
3. 接口测试如何做参数化与数据驱动？
4. 接口测试与 UI 自动化测试的区别与互补？

**解析**
1. **Q1（接口校验内容）**：① 状态码；② 响应体字段值/类型（JSON Path 断言）；③ 响应时间（性能基线）；④ 业务状态码/错误码；⑤ 数据结构 Schema；⑥ 安全（越权、注入）；⑦ 依赖数据落库（配合 SQL 校验）。
2. **Q2（数据依赖/关联）**：用**关联提取**——从上一个接口响应中提取值（正则 / JSON Path / XPath），存为变量/环境变量，传给后续接口。典型：登录提取 `token` → 设全局变量 → 后续接口请求头引用。
3. **Q3（参数化/数据驱动）**：把测试数据抽到外部（CSV / JSON / Excel / 环境变量），脚本循环读取每行执行同一逻辑，一份脚本覆盖多组数据。**好处**：用例与数据解耦、易维护、覆盖边界。
4. **Q4（接口 vs UI 自动化）**：接口层快、稳、易定位、覆盖后端逻辑；UI 层慢、脆、贴近用户但易因前端变动失败。**互补**：接口保证「对」，UI 保证「能用」，优先接口自动化、UI 覆盖核心链路。

### 2.4 抓包与问题定位

| 工具                | 用途                       |
| ----------------- | ------------------------ |
| Fiddler / Charles | HTTP 代理抓包、断点篡改、弱网模拟      |
| Wireshark         | 网络层抓包、TCP 重传/丢包分析        |
| Chrome DevTools   | 前端请求、Timing 分析、Source 调试 |
| Postman / curl    | 单接口手动调试                  |

**必会题**

1. 接口返回 500，但前端只显示"网络错误"，如何定位？（抓包看真实响应体）
2. 如何用 Charles 模拟弱网？
3. 前端说"接口慢"，后端说"很快"，怎么查？（看 TTFB、网络往返、前端处理耗时）

**解析**
1. **Q1（500 vs 网络错误）**：前端「网络错误」往往是**捕获异常后统一提示**，真实错误藏在响应体。用 **Charles/Fiddler/DevTools Network** 抓包看实际 `status` 与 `response body`，定位是后端 500（看后端日志/堆栈）还是前端误处理。
2. **Q2（Charles 弱网）**：Charles → Proxy → Throttle Settings，选预设（如 3G/56k）或自定义带宽/延迟/丢包率，开启后对指定 host 限速，验证前端弱网下的超时、重试、loading 表现。
3. **Q3（前端慢 vs 后端慢）**：看 Network 面板 **Timing**：`TTFB`（首字节时间，大=后端慢）、`Content Download`（传输慢=网络/包大）、其余为前端渲染耗时。后端说快可对比服务器内网调用耗时 vs 公网 TTFB，定位是网络往返还是前端处理。

### 2.5 认证与安全基础

- **Token 机制**：JWT 结构（Header.Payload.Signature），过期与刷新。
- **加密**：对称（AES）vs 非对称（RSA）。
- **常见安全测试点**：SQL 注入、XSS、越权（水平/垂直）、敏感信息泄露。
- **幂等性**：重复提交同一请求结果一致（自动化中重试机制需注意）。

**必会题**

1. 什么是接口幂等性？自动化测试中为什么要关注？
2. 常见接口安全漏洞有哪些？如何测？

**解析**
1. **Q1（幂等性）**：同一请求**重复执行多次，结果一致**（如支付接口重复调用不应重复扣款）。自动化中要关注：重试机制、网络超时重发可能导致**重复提交**，需设计幂等（唯一流水号/Token/去重表）。测试时可重复发同一请求验证结果不变。
2. **Q2（安全漏洞）**：常见——SQL 注入、XSS、越权（水平：改 ID 看他人数据；垂直：普通用户调管理员接口）、敏感信息泄露、重放攻击。**怎么测**：注入 payload 验证过滤、用低权限 token 调高权限接口验证拦截、改参数 ID 验证越权、看响应是否泄露密钥/明文密码。

### 2.6 WebSocket 专项（实时通信测试）

WebSocket 是接口测试中越来越常被问到的点，尤其 IM、推送、行情、协同编辑类系统。

**核心概念**

- **是什么**：基于 TCP 的全双工长连接通信协议，诞生于 HTML5，默认端口 80（ws）/ 443（wss）。
- **与 HTTP 的关系**：握手阶段用 HTTP（`Upgrade: websocket` 头），握手成功后协议升级，脱离 HTTP，双方可主动互发数据帧。
- **与 HTTP 长轮询的区别**：长轮询是「客户端反复问」，WebSocket 是「服务端主动推」，连接建立后不再频繁握手，延迟低、开销小。

| 对比维度   | HTTP / 长轮询 | WebSocket      |
| ------ | ---------- | -------------- |
| 通信方式   | 请求-响应，单向   | 全双工，双向         |
| 连接生命周期 | 短连接（用完即关）  | 长连接（持续保活）      |
| 谁可主动发  | 仅客户端       | 客户端和服务端均可      |
| 实时性    | 依赖轮询间隔，有延迟 | 服务端实时推送        |
| 头部开销   | 每次请求带完整头   | 握手后仅 2~14 字节帧头 |

**握手过程（面试常让描述）**

```
客户端请求：
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

服务端响应（状态码 101 Switching Protocols）：
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

**关键字段 / 机制**

- `Sec-WebSocket-Key`：客户端随机生成，服务端用固定算法 + 固定 GUID 算 `Sec-WebSocket-Accept` 返回，用于握手合法性校验。
- **数据帧（Frame）**：消息被切分成帧，含 `FIN`（是否为消息最后一帧）、`opcode`（数据类型：1=文本，2=二进制，8=关闭，9=ping，10=pong）、`Mask`（客户端发往服务端必须掩码）。
- **心跳保活**：通过 `ping/pong` 帧检测连接存活，防止 NAT/代理超时断开。
- **断线重连**：客户端需实现指数退避重连 + 重订阅机制。

**高频题**

1. WebSocket 和 HTTP 有什么区别？为什么说它「基于 HTTP 但又脱离 HTTP」？
2. WebSocket 握手的具体过程是什么？状态码 101 代表什么？
3. 为什么 WebSocket 比轮询更适合实时场景？
4. `Sec-WebSocket-Key` 和 `Sec-WebSocket-Accept` 的作用是什么？
5. 客户端发消息为什么要做掩码（Mask）？服务端发消息呢？
6. 如何判断 WebSocket 连接是否已断开？怎么做断线重连？
7. `wss` 和 `ws` 的关系，等同于 HTTPS 和 HTTP 吗？

**逐题解析（含关键字含义）**

**Q1. WebSocket 和 HTTP 有什么区别？为什么说它「基于 HTTP 但又脱离 HTTP」？**

- 区别：HTTP 是「请求-响应」单向短连接，每次通信都由客户端发起；WebSocket 是握手后建立的**全双工长连接**，连接建立后服务端可主动推送，双方随时互发数据。
- 「基于 HTTP」：建立连接的那一次用的是 HTTP 请求（`GET` + `Upgrade: websocket` 头），靠 HTTP 完成协商。
- 「脱离 HTTP」：握手成功后协议升级，后续数据走 WebSocket 自己的**帧（Frame）**&#x683C;式，不再携带 HTTP 头、不再走 HTTP 语义，所以开销极小、延迟极低。
- **关键字**：全双工（双向同时通信）、长连接（连接持续保活）、短连接（用完即断）、协议升级（Upgrade）。

**Q2. WebSocket 握手的具体过程是什么？状态码 101 代表什么？**

- 客户端发一个 HTTP `GET` 请求，带关键头：`Upgrade: websocket`、`Connection: Upgrade`、`Sec-WebSocket-Key`（随机 16 字节 Base64）、`Sec-WebSocket-Version: 13`。
- 服务端校验通过后，返回 **`101 Switching Protocols`**，并带 `Sec-WebSocket-Accept`（由客户端的 Key + 固定 GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11` 经 SHA-1 + Base64 算出），确认协议切换成功，连接转为 WebSocket。
- **关键字**：`101 Switching Protocols`（协议切换成功的状态码）、`Sec-WebSocket-Key`（客户端随机数，防缓存/伪装）、`Sec-WebSocket-Accept`（服务端校验应答）、`Version 13`（当前标准版本）。

**Q3. 为什么 WebSocket 比轮询更适合实时场景？**

- **轮询/长轮询**：客户端反复发 HTTP 请求问「有新消息吗」，每次都带完整 HTTP 头，服务端无数据时也只能空回，浪费带宽且受轮询间隔限制，实时性差。
- **WebSocket**：一次握手后连接常驻，服务端有消息立刻推，无额外握手与头部开销，毫秒级延迟，连接数可控。
- **关键字**：轮询（定时主动问）、长轮询（挂起等待直到有数据才返回）、实时性（低延迟）、头部开销（每次请求重复的元数据）。

**Q4. `Sec-WebSocket-Key` 和 `Sec-WebSocket-Accept` 的作用是什么？**

- `Sec-WebSocket-Key`：客户端随机生成的 Base64 串，服务端用它 + 固定 GUID 做 SHA-1 哈希再 Base64 得到 `Sec-WebSocket-Accept` 返回。
- 作用：① 确认服务端**真的懂 WebSocket 协议**（不是随便回 101）；② 防止被缓存的静态响应误当成握手成功；③ 防止非预期的连接（如误代理）。
- 注意：它**不是加密、不是鉴权**，只是握手合法性校验，不能防中间人。
- **关键字**：SHA-1（哈希算法）、GUID（全局唯一标识符，此处为协议固定值）、握手校验（确认双方协议一致）。

**Q5. 客户端发消息为什么要做掩码（Mask）？服务端发消息呢？**

- **掩码（Mask）**：客户端发往服务端的每一帧数据，payload 必须用随机 32 位掩码键做 XOR 异或加密（`Mask=1`）。
- 目的：防止**缓存污染攻击**——早期设计担心恶意网页通过 WebSocket 伪造看似来自其他站点的请求，污染共享缓存/代理。规范要求客户端发送必须掩码。
- 服务端 → 客户端**不需要掩码**（`Mask=0`），因为服务端是可信的，且浏览器端不需要防缓存污染。
- **关键字**：掩码（XOR 混淆 payload）、`Mask` 标志位、缓存污染（伪造请求污染中间缓存）、XOR（异或运算）。

**Q6. 如何判断 WebSocket 连接是否已断开？怎么做断线重连？**

- 判断断开：① 收到 `opcode=8` 的**关闭帧（Close Frame）**；② 心跳 `ping` 后超时未收到 `pong`；③ 底层 TCP 错误 / `onerror` / `onclose` 触发。
- 断线重连：监听 `onclose`，用**指数退避**（如 1s、2s、4s… 上限封顶）重试，重连成功后**重新订阅**之前的频道/恢复会话（带 reconnect token 或 last-message-id 做增量补推）。
- **关键字**：关闭帧（opcode 8）、心跳（ping/pong 保活）、指数退避（重试间隔翻倍）、重订阅（恢复订阅状态）。

**Q7. `wss` 和 `ws` 的关系，等同于 HTTPS 和 HTTP 吗？**

- `ws` = 明文的 WebSocket（默认端口 80），`wss` = 基于 **TLS 加密**的 WebSocket（默认端口 443），关系与 HTTP/HTTPS 完全一致：`wss` 就是「WebSocket over TLS」。
- 等同点：都是「明文 vs 加密」的对应关系，生产环境必须用 `wss`（否则 token、消息内容明文裸奔，还容易被代理拦截）。
- 不等同的细节：`wss` 加密的是整个 WebSocket 连接，包括握手，所以比「HTTP 升 HTTPS」更彻底；且 `wss` 能穿透只允许 443 的企业防火墙，而 `ws`(80) 常被拦。
- **关键字**：`ws`（明文）、`wss`（TLS 加密）、TLS（传输层安全协议）、默认端口（80 / 443）。

**自动化测试要点（岗位结合）**

- **连接测试**：能否成功握手建立连接，异常参数（错误 key、不支持的 version）是否被拒。
- **消息收发**：发送约定格式消息，校验服务端返回/推送内容、顺序、时序。
- **心跳与超时**：模拟心跳停止，验证连接是否在预期时间内断开或重连。
- **并发与压测**：大量连接同时在线（用 `websocket-client` / `Locust` + WebSocket 协议）验证服务端承载能力。
- **弱网 / 断网**：网络抖动下消息是否丢失、重连后是否补推。
- **断言工具**：Python 可用 `websocket-client`、`pytest`、`asyncio` + `websockets` 库写自动化用例。

```python
import websocket, pytest

def test_ws_echo():
    ws = websocket.create_connection("wss://echo.example.com")
    ws.send("hello")
    assert ws.recv() == "hello"   # 校验回显
    ws.close()
```

## 三、综合实战场景题（真实故障视角）

> 下面都是真实项目里高频踩坑的场景。每个场景按「**现象 → 测试排查方案 → 可沉淀的自动化点**」组织，重点不在"会不会写"，而在"能不能从测试角度定位并防住"。

### 场景 1：下单接口返回成功，但库存没扣 / 出现超卖

**现象**
- 接口返回 `200`、前端提示下单成功；运营却发现某商品库存还是满的，或库存变成了负数（超卖）。
- 接口自动化「全绿」，因为用例只断言了 HTTP 状态码和响应体，`没有查库`。

**测试排查方案**
1. 接口断言不能只看状态码——下单后必须 `SELECT` 校验：**订单状态、库存扣减值、资金流水**三者一致。
2. 用 SQL 核对跨表一致性：`orders.amount` 与 `payments` 合计、`goods.stock` 扣减量 = 下单数量。
3. **并发超卖专项**：用压测工具（JMeter/Locust）起 50 个并发抢同一件商品（库存=10），验证最终库存不为负、不超 10 单——暴露库存竞态（缺分布式锁/乐观锁版本号）。
4. 查应用日志确认扣减逻辑是否在事务内、是否有异常吞掉。「在事务内」指**库存扣减和下单必须包在同一个事务里**——任一步失败整体回滚，才不会"下了单没扣库存"或"扣了库存没下成单"。反例：两步分开提交，网络抖动导致第二步失败，数据就撕裂不一致了（正确写法见下）：
```sql
BEGIN;
UPDATE goods SET stock = stock - 1 WHERE id = 100 AND stock >= 1;  -- 扣库存（带余量校验）
INSERT INTO orders(...) VALUES (...);                              -- 下单
COMMIT;   -- 两步同时成功才提交；任一步失败 ROLLBACK，库存自动复原
```

**可沉淀的自动化点**
- 下单用例后置 SQL 校验模板（状态+库存+流水三联查）。
- 库存并发竞态用例（固定库存高并发），作为上线卡点。

---

### 场景 2：测试环境稳过，生产偶现接口超时

**现象**
- 测试用例在测试环境 100% 通过；生产监控却报某接口偶发超时（>3s）。
- 开发本地也复现不了——因为**测试库只有几万条数据，生产有上亿条**。

**测试排查方案**
1. 第一步怀疑**数据量差异导致的慢 SQL**：对生产慢查询日志里超时的 SQL 跑 `EXPLAIN`，看是否 `type=ALL`（全表扫描）、`key=NULL`（没走索引）。
2. 在测试环境**造大数据量**（灌入与生产同量级或同分布的样本）复现，再验证加索引后是否好转。
3. 抓包看 `TTFB`：若 TTFB 大=后端慢（SQL/外部调用）；若 TTFB 小但总时长长=网络/传输问题。
4. 查网关/应用日志定位超时发生在哪一层（DB、下游 RPC、还是自身逻辑）。

**可沉淀的自动化点**
- 核心接口**性能基线断言**（响应时间 P95 < 阈值）。
- 大数据量回归库 + 定时 `EXPLAIN` 巡检脚本，防止索引被误删。

---

### 场景 3：弱网/超时重试导致重复下单、重复支付

**现象**
- 用户在地铁里（弱网）点"支付"，前端等不到响应给了"失败"，用户再点一次——结果**扣了两次款 / 下了两单**。
- 这是典型**幂等性缺失**：重试请求没有去重。

**测试排查方案**
1. 用 Charles/Fiddler 限速（模拟 3G / 高延迟）制造超时，触发前端自动重试或用户重复点击。
2. 用**同一个幂等键（idempotency-key / 订单令牌）**重复发两次创建订单请求，断言：只生成 1 笔订单、只扣 1 次款。
3. 验证防护组合：前端防重复点击（按钮置灰）+ 后端唯一令牌去重表 + 重试带同一 key。
4. 边界：令牌过期、并发同令牌是否被同时放行（需 DB 唯一索引兜底）。

**可沉淀的自动化点**
- 幂等专项用例：相同 key 重复提交 N 次 → 仅 1 次生效。
- 弱网重试用例接入 CI，覆盖"超时→重试→不重复"路径。

---

### 场景 4：支付回调延迟/丢失，订单卡在"支付中"

**现象**
- 用户已付款，但订单长时间显示"支付中"或"待支付"；偶尔（回调失败）直接变"支付失败"但钱已扣。
- 异步**回调（callback/webhook）**是测试最容易漏的环节——同步接口断言过了，但回调没验证。

**测试排查方案**
1. 区分同步响应与异步回调：下单/支付接口只返回"受理成功"，真实状态由第三方回调更新，**不能同步断言最终态**。
2. 用 **Mock 回调**或沙箱环境主动推送回调，验证订单状态机正确流转（待支付→支付中→已支付/失败）。
3. 测回调**可靠性**：模拟回调超时/网络丢包，验证服务端是否有重试 + 幂等（同一笔流水不重复入账）。
4. 核对：回调失败时应有补偿/对账任务，而非让用户一直"支付中"。

**可沉淀的自动化点**
- 回调链路用例：发支付 → Mock 回调 → 断言状态流转 + 查库金额一致。
- 回调失败重试用例（断言不重复入账）。

---

### 场景 5：接口改了字段，老客户端解析失败/崩溃

**现象**
- 后端给响应加了个必填字段、或把 `amount` 改成字符串，新前端没问题，**老版本 App 直接白屏/解析异常**。
- 接口"向前兼容"被破坏，但接口自动化只测了最新契约，没覆盖老版本。

**测试排查方案**
1. 推动**契约测试**（如 Pact）：锁定 request/response 的 schema，任意一方改动破坏契约就报警。
2. 回归**多版本客户端**对同一个接口的兼容性（老字段是否还在、类型是否变）。
3. 监控告警：响应里出现字段缺失 / 类型不符时快速发现，而非等用户投诉。
4. 接口变更流程：破坏性变更必须带版本号（`/v1/`、`/v2/`），老版本并行保留一段时间。

**可沉淀的自动化点**
- 契约测试接入 CI，接口与消费方 schema 双向校验。
- 多版本兼容回归套件。

---

### 场景 6：WebSocket 断网重连后消息丢失或重复

**现象**
- IM/推送场景：地铁进隧道断网，回来后**部分消息没收到**，或**同一条消息弹了两次**。
- 实时通信的可靠性（不重不漏、有序）是测试盲区。

**测试排查方案**
1. 模拟断网→重连（Charles 断流 / 杀掉网络），验证服务端是否按 **`last-message-id` / 序列号**补推断连期间消息。
2. 客户端按 `msgId` **去重**，验证重连后不重复弹窗。
3. 校验**顺序**：消息 seq 递增、无乱序；心跳（ping/pong）超时应触发重连而非假死。
4. 同时做两件事：监听 `onmessage` 回执帧断言内容 + 查库断言落库一致（双保险）。

**可沉淀的自动化点**
- 断网重连用例：断流→恢复→断言消息不重不漏且有序。
- 心跳超时用例：停发 ping → 验证连接判定断开并自动重连。

---

### 场景 7：并发用例偶发失败，查是脏数据串扰（测试工程内功）

**现象**
- 单跑每条用例都过，**并发/夜间批量跑就偶发失败**；排查发现用例 A 写的数据被用例 B 读到，互相污染。
- 这是自动化测试工程最常见的"玄学失败"。

**测试排查方案**
1. 隔离策略三选一或组合：**事务回滚**（跑完 ROLLBACK）、**独立测试库**、**动态唯一数据**（每条用例随机前缀/UUID）。其中「事务回滚」落地最简（对应 1.5 节示例）：每条用例 `BEGIN` 开头、`finally` 里 `ROLLBACK` 收尾，数据不留库：
```python
def test_case():
    db.execute("BEGIN")
    try:
        # ... 造数 / 调接口 / 断言
        pass
    finally:
        db.execute("ROLLBACK")   # 无论成功失败都回滚
```
2. 清理机制：测试前/后执行清理脚本，且清理用精确条件（按用例标记），避免误删他人数据。
3. 并发安全：CI 并行时给每条用例分配独立数据空间或串行化强依赖用例。
4. 失败定位：失败时用唯一用例 ID + 时间戳反查是哪条数据串扰，而非盲目加重试。

**可沉淀的自动化点**
- 统一测试数据工厂（DataFactory）+ 事务回滚框架。
- 并发隔离基线用例，作为 CI 稳定性门禁。

## 四、复习建议

- **SQL**：每天手写 5 道（JOIN + 子查询 + 聚合），重点练 `LEFT JOIN` 过滤条件位置、`NOT IN` 的 NULL 陷阱、`EXPLAIN` 读执行计划。
- **网络**：背熟状态码表 + TCP 握手 + HTTPS 流程，能在白板上画出来。
- **结合岗位**：自动化测试不只考"会写 SQL/懂网络"，更考"用它们解决测试问题"——多从「数据校验」「接口断言」「问题定位」角度组织回答。
